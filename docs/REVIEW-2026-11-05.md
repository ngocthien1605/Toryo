## Verdict

No Critical and no High finding. The boundary's design holds: the export is byte-checked against what Git must write, the path policy sees the index as well as the tree, the reader refuses nothing it is unsure of. The holes are at its **edges**:

- **What Toryo trusts without checking.** It trusts a run-store file to say which folder verify may `clean -ffdx` and `task cleanup` may delete (T7). It trusts the worktree's `.git` pointer to say where the Git metadata it protects lives (T2).
- **When it checks.** The path policy runs one step before the `git add -A` that builds the checkpoint, and the commit is never checked (T4).
- **What the M18 reader does not read.** It misses the `sh` keywords `if` / `then` / `while`, and the launchers `cmd start` and `pwsh -CommandWithArgs` (T5). It misses `+` options, unlisted valued flags and versioned interpreter names (T6).

Fix T7 first. It is the only finding where one forged file leads to an irreversible loss: a recursive delete of any folder, run by the owner's routine `task cleanup`, and `R23-24` did not cover that path. T4 and T2 are O-34 (review 2026-10-01 M7 and M4), now **reproduced** — they were "medium confidence" reading findings. T5 is the X7 hole (the implementer writes its own gate) reopened through spellings that are common in real gate scripts.

## Findings (priority 1)

### Verify: the checkout record

T7. **A forged `verify-checkout.json` makes verify reset and clean any folder, and makes `task cleanup` delete any folder.** `verify.rs:377-378`: `prepare` takes `<run store>/runstore/verify-checkout.json` when `c.dir.exists() && c.admin.exists() && c.low == low && c.base == base`. `base` is compared with `<verify_root>/<task>`; `dir` and `admin` are not compared with anything. Then `:426` writes the recorded `pointer` into `<dir>/.git`, `:429` runs `checkout -q --detach --force <sha>` and `:434` `clean -ffdx` with `Loc::Explicit { git_dir: admin, work_tree: dir }`. `verify.rs:1176-1194` `cleanup` takes `base` from the same record and runs `remove_dir_all` on it. `engine_cli.rs:529` (`cleanup_confined`, R23-24) confines the row's worktree and run store first, then `:555` calls `verify::cleanup` with no such check.

The record is a plain `std::fs::write` (`verify.rs:420`), outside the artifact SHA registry that N-11 names as "the real guard for agent-written run-store files". Yet it decides what R47 pins: which Git directory and which work tree the verify side's Git uses. It also decides the Git directory the environment-gate export reads its objects from (`deploy_source`, `:677`; `bytes_are_the_commits`, `:985`). So the byte check of the export compares against an object store the record chose. That consequence is `read`, not reproduced. `reproduced`:

- With `dir` set to a folder holding an untracked file and `admin` set to the repository's own `.git`, a normal `toryo run` deleted the file. It also detached the owner's `main` HEAD in the main repository (`HEAD` was `refs/heads/main`, after the run it is not a symbolic ref).
- With `base` set to a folder, `toryo task cleanup T-1 --force` deleted the folder and exited 0.

Precondition: write access to the run store — outside both vendor sandboxes, inside N-11's "an agent started with the owner's token". It is Medium rather than Low (the 2026-10-23 review rated the cleanup half of N-11 Low) because the damage is irreversible, the trigger is a routine owner command, and R23-24 promised "cleanup deletes only its own folders". Fix:

- In `prepare`, accept the record only when `dir == base.join("<id>.verify")`, `admin` canonicalises to an entry under `<repo common dir>/worktrees/`, and that entry's `gitdir` file names `dir/.git`. Otherwise make a new checkout, as for a missing record.
- In `cleanup`, delete only `verify_root(cfg).join(&t.id)` (or the record's `base` when it equals that), never a recorded path as such.
- Better still, write the record through `artifacts::put`, so that a change is `artifact_tampered`.

### Write fence and path policy: the checkpoint

T4. **The path policy is asked of `git status`; the commit is made by a later `git add -A` and is never checked (O-34, review M7: now reproduced).** `runner/checkpoint.rs:88-104`: `wt.changed()` → `violates()` (protected, denied, outside the write fence). Then `:105` `nothing_to_commit()` runs `git add -A` (`worktree.rs:182`), and `:115` `commit()` runs it again (`worktree.rs:160`) and commits. After the commit only `protect::check` runs (`:142`). It escalates on *untracked/ignored* protected changes and Git metadata, so a protected file that is now **tracked** in the checkpoint is not hard and passes. A *found* commit gets the full policy (`recovery.rs:38` `foreign_commit`); a fresh one does not. The write fence is enforced only by this check, so the same window carries a path outside `writes:` or on `never:`.

`reproduced` with a `TORYO_GIT` wrapper in the role of a process that outlived the turn. Just before the first `git add -A` in the task worktree, it appends a line to the tracked, protected `AGENTS.md`. The run ends with `AGENTS.md` in `base..HEAD` of the task branch, next to the implementer's `src/Calculator.psm1`, and nothing escalates. Who can be that process `read`:

- On Unix, anything that called `setsid` (the process group is not a boundary: review M7).
- On Windows, a process started through WMI (`Win32_Process.Create`) or the task scheduler, whose parent is not in the Job.

Fix:

- After `commit`, ask `violates()` of `changed_between(anchor, sha)` — the question `foreign_commit` asks of a found commit. On a violation, soft-reset to the anchor and escalate `policy_violation`.
- Alternatively, stage exactly the checked paths (`git add -- <pathspec of the checked list>`, literal pathspecs), so that what is committed is what was asked.
- Also escalate on `!tree_gone` (M7's own advice).

### M18: the command-line reader

T5. **`sh` keywords and launchers hide the head of a simple command.** `cmdline.rs:618-626` takes the head after `call`, `exec`, `time`, `source`, `.` and assignments (and `do` / `else` for `cmd`). For `sh` the keywords `if`, `then`, `elif`, `else`, `while`, `until`, `do` and the builtin `command` are not prefixes. So in `sh -c 'if ./scripts/check.sh; then …; fi'`, `if true; then ./x.sh; fi`, `while ./x.sh; do …`, `until …` and `command ./x.sh` the script is an **argument**. The same happens elsewhere:

- `cmd`: `start` (`:149`) and `if` (`:129`) are in `CMD_BUILTINS` ("a bare head that is one of them runs no file"). Both run the command after them: `cmd /c start /wait scripts\x.cmd`, `cmd /c if exist f scripts\x.cmd`.
- PowerShell 7.4's `-CommandWithArgs` / `-cwa` is not a command flag (`checks.rs:1074`), so `pwsh -cwa "& ./x.ps1"` is not read as a command string. `pwsh -cwa ./x.ps1` is still caught by the `.ps1` rule.

An argument is never refused (X10), and it is protected only when the base commit already has it (`verify_files_at_base`). A gate that names a script the task is meant to add is therefore neither refused at `task create` nor protected: the implementer writes the gate, and X7 is open again. `if ./check.sh; then` is a common way to write a gate. `reproduced` (nine forms, all `[]`). The wrappers `env`, `timeout` and `!` are O-41 and are not counted here. Fix:

- `sh`: treat the keywords and `command` as prefixes (the word after them is a head; `!` with them closes part of O-41).
- `cmd`: skip `start`'s switches and an optional quoted title to its head, and `if`'s condition (`not`, `/i`, `exist <x>`, `errorlevel <n>`, `defined <x>`, `<a>==<b>`, `<a> <op> <b>`) to its command.
- PowerShell: `-CommandWithArgs` / `-cwa` is a command flag whose string is the next argument only.

T6. **(Low) Option and interpreter spellings put the wrong word in the script's place.** Outside a command string, `entry_scripts` (`checks.rs:1260-1345`) takes the first argument that does not start with `-` and is not the value of a listed flag (`INTERPRETERS`, `:955`). These spellings defeat that rule:

- **`+` options.** `bash +o posix x.sh` and `sh +x x.sh`: the entry is `+o` / `+x`.
- **Unlisted valued flags.** `node --experimental-loader ./l.mjs x.js`: the entry is the loader, not `x.js`. `node --inspect-port 9229 x.js`: the entry is `9229`. `python --check-hash-based-pycs always x.py` behaves the same way (probe).
- **Versioned interpreter names.** `python3.12 x.py` (the usual spelling on Linux CI; also `perl5.x`, `ruby3.x`) is no interpreter at all: no entry.
- **`cmd /r x.cmd`.** `/r` is `/c` to `cmd.exe` (`read`: `cmd.exe` was not run here), but `checks.rs:1113` knows `/c` and `/k` only.

In each case the real script, missing at base, is neither refused nor protected. `reproduced` (the reader). Fix:

- In `SH_FAMILY`, read a `+` option like a `-` one, with `+o` taking a value.
- When the first positional word has no separator and no extension but a later one has, take the later one as the entry: never refusable from the first.
- Map `^(python|pypy)3(\.\d+)?$` and the like to their table entry.
- Accept `/r` with `/c` and `/k`.

### The protected-state scan

T2. **The worktree's `.git` pointer is not protected state, and the scan reads the Git metadata through it (O-34, review M4: now reproduced, with a consequence M4 did not name).** `protect.rs:209` skips every entry named `.git`. `git_meta` (`:107`) finds the common dir with `rev-parse --git-common-dir` from the worktree, that is, through the pointer. Every other Git call on the task worktree discovers the same way (`worktree.rs` `Loc::Discover`). The verify checkout got R47 for this very pointer; the task worktree did not.

`reproduced`: the test points `.git` at a byte-identical copy of the Git directory, with the task's HEAD and index, and then adds a `post-checkout` hook to the **real** Git directory. The scan reports nothing, because it now hashes the copy's `config`, `hooks/`, `info/*` — equal to the baseline — and never looks at the real ones. The pointer is inside the implementer's writable root. Whether a vendor sandbox protects a `.git` *file*, as Codex protects a `.git` *folder*, is not known here (`read`). The hook itself needs a write outside the worktree, which is what R35's `@git/` entries exist to catch. Fix (M4's):

- Record `--absolute-git-dir` and `--git-common-dir` at `task create`, and use `Loc::Explicit` for every task-worktree Git call, `git_meta` included.
- Add the pointer's bytes to the snapshot as `@git/pointer`; a change is hard.

T1. **(Low) A packed replace ref is not protected Git metadata.** `protect.rs:163-183` lists loose `refs/replace/*` only. A ref that only ever existed in `<common>/packed-refs` (`git replace …; git pack-refs --all`, or any `git gc` before the next scan) is not seen. `reproduced`: after `replace` + `pack-refs` the task's `HEAD:src/a.txt` shows the other commit's content, and the scan reports `[]`.

M13-NOTES R1 records this as "Not covered" and dismisses it because Toryo's own Git sets `GIT_NO_REPLACE_OBJECTS`. But X30's point was the *second* line: Git everywhere else honours the ref. That includes the reviewer agent's `git show`, the owner's `git log` and `git merge toryo/<id>` in the shared repository. So what the owner merges after the final approval can be another tree than the one reviewed and verified. It is Low because writing `packed-refs` needs the same out-of-worktree write as T2's hook. Fix: add each `refs/replace/*` line of `packed-refs` to the `@git/` set (or `git for-each-ref refs/replace` through the hardened `GitCmd`, which also covers a reftable backend), and record the STATUS row that M13 never opened.

T3. **(Low) Nested `.git` entries are skipped although `.git` is a protected directory name.** `checks.rs:291` puts `.git` in `PROTECTED_DIRS` ("protected at any depth"), so `Protected::matches("src/sub/.git/config")` is true. But `protect.rs:209` skips every `.git` before it asks. A nested repository that the implementer creates inside its fence (`src/sub/.git/config` with `core.fsmonitor = …`, or a hook) is unseen by R35 and by `git status` (which lists `src/sub/` only). `git add -A` makes it a gitlink of the checkpoint, and `allow_submodules` looks only for `.gitmodules`. Any Git started inside `src/sub/` runs it with the owner's rights: an editor, a shell prompt with Git status, a reviewer that runs `git -C src/sub log`, the owner after the merge. `reproduced` (the scan's `[]`). Fix: skip only the worktree's own root pointer (handled by T2); record a nested `.git` as a protected entry (its `config` and `hooks/*` hashed, or the entry itself, so that its appearance is a hard change), and refuse a gitlink in a checkpoint when submodules are not allowed.

## What held up (adversarial reading and probes, no finding)

- **The export comparison** (`deploy_source`, `bytes_are_the_commits`, `export_changed`):
  - every entry of the folder is accounted for (files, empty folders, links, `Other`, a `.git` entry);
  - framing by the on-disk size can only report, never accept, a length mismatch: the remainder of a longer answer would have to parse as the next request's header for the same object id, and the bytes on disk are Git's own `checkout-index` output;
  - `write-tree` equals `<head>^{tree}`;
  - links are exported as files;
  - case folding on Windows refuses a tree that could not be checked out.

  Its remaining limits are O-47, O-48 and O-49. The one way around it found here goes through the record that names its Git directory (T7).
- **The change list** (`git status --porcelain=v1 -z --untracked-files=all --no-renames`) shows index-vs-HEAD differences in the X column. A blob staged by an agent, or kept under `skip-worktree` / `assume-unchanged`, is listed and judged before `git add -A` (`read`). The renames-off rule makes a rename's source reach the policy (EC-26).
- **Fence patterns**: refused syntax, `..`, absolute paths, variables and shortcuts are refused at load; `x` names `x/**`; a wildcard without `/` matches at any depth; `never` wins over `writes`; `## Allow protected` opens both (R61). O-53 stands.
- **Protected names**: case-insensitive (EC-09); a link at a protected name is recorded, never followed (EC-08); a FIFO is not opened. Claude runs with `--safe-mode` and gets `CLAUDE.md` from Toryo's context loader, so `@imports` inside `CLAUDE.md` are not a way in. The Claude implementer has no shell tool.
- **`.toryo-tmp`** is excluded from the scan and the snapshot, but it is emptied link-safely (`remove_dir_all` does not follow a link) at the start of every implementer turn, and no tool Toryo starts loads configuration from it.
- **M18 forms read correctly** (probe): `cd` / `pushd` / `Set-Location -Path` followed or stopped as documented, including `(cd x; …)` and `cd x || exit`. Also read correctly:
  - `sh`: `&&`, `{ …; }`, a function definition, `<` redirections, the clusters `-ec` / `-ce`, `--` and `-`;
  - PowerShell: the abbreviations `-co`, `-com`, `-Comm`, `-Fi`, `-fil`; `& 'quoted'`, `&./x`; `.\x;exit $LASTEXITCODE`; `-cwa ./x.ps1` (through the `.ps1` rule);
  - `cmd`: `cmd.exe /d /s /c`, `for /f … ('x.cmd')`, and a bare `cmd` head expanded over `PATHEXT`.

## Leads not pursued (not findings)

- `prepare` and `deploy_source` read objects through the record's `admin`. Whether Git verifies a loose object's hash on the read paths `checkout-index` and `cat-file --batch` use was not checked. If it does not, T7 also lets a forged object store pass the byte check of the export. Fixing T7 closes it either way.
- On a case-sensitive file system the fence and the protected names still compare case-insensitively: `writes: [Metadata/**]` admits `metadata/x` as a different folder. This over-permits on Linux only; the D365FO target is NTFS.
- Toryo cannot see whether the vendor sandboxes treat a `.git` *file* (a worktree pointer) as they treat a `.git` folder. That decides whether T2's first step is in the implementer's reach without any escape: one measurement with each vendor on the real machine.
