# Toryo — decisions in force

One line per decision. **Status** says whether it stands or was replaced (the replacement is named). "Where" is the place in the
code that carries it. The R-numbers (R1 … R72) in the code and the notes come from the plan v0.8 (`plan-v0.8.md`, **not in this
repository**) and from the review rounds of M11; `docs/archive/M11-NOTES.md` has the record per round. This file is the input for
plan v0.9. Add new decisions here; never restate them in a new notes file.

(M13-R4) | in force | `engine/runner.rs` `undo_read_only_write`, `could_not_undo`, `finish_pending_undo`; `engine/recovery.rs` `undo_before_early_return`, `read_only_end` |
| **X33** | Text that reaches a console is inert: every human-readable line of the engine and the CLI is printed through `errln!` / `outln!` (or `term::text`), which remove ANSI escape sequences whole, drop carriage returns and turn every other control character and every zero-width or direction-changing character into `�` (the tab and the line feed stay). `--json` output and the recorded events keep what was sent (JSON escapes it); `toryo context show` is byte-exact into a pipe and inert on a terminal. A bare `println!` / `eprintln!` outside the M0 kit and the tests fails `m15_console_text_goes_through_the_terminal_filter`. (M15-01, review M9) | in force | `src/term.rs`, `engine/flight.rs` `render`, `tests/m15_terminal.rs` |
| **X34** | Colour is a property of the stream, never of the text. Toryo's own lines are painted only when the stream takes colour (`--color auto` on a terminal, with the `NO_COLOR` / `CLICOLOR_FORCE` conventions; `always`; `never`); into a pipe or a file the output is the plain text of before, and `--json` is never painted. Painting changes no character (with the sequences removed the painted text is the text) and reads a line's meaning from its shape, so `run` and `watch` paint alike. Only the first line of a printed block is painted (and the `next:` line under an end banner, the `→` line): a plan, a review and the further lines of a reason are text somebody else wrote and stay unpainted — on a terminal, colour marks the lines that are Toryo's own. Painted, a run ends in an open frame (no right edge, no width arithmetic) instead of the `══════════` banner. Nothing outside `src/term.rs` and `src/term/paint.rs` writes an escape sequence. (M15-02) | in force | `src/term.rs` `painted`, `try_line`, `quoted`, `end_block`; `src/term/paint.rs` |
| **X35** | `toryo dashboard` is read-only and speaks only Toryo's words. It reads the store (`Store::read`, never `BEGIN IMMEDIATE`) and each task's `events.jsonl`, takes no task lock and writes nothing, so it never refuses or slows a run. A task's lines are its `status` row, `now:` (the stage that started and has not finished in the newest run — only while the recorded lock owner is alive: after a crash it is history), `last:` (the newest event as a few words) and `next:`. No free text of an event reaches it: an escalation shows its `reason_class`, a pause, an error, an owner label or a plan nothing — the reasons are read with `watch` or `status`. On a terminal it redraws in place (cursor home, erase to line end, erase below — written only by `src/term.rs` `screen`, X34); into a pipe or a file it prints one frame. (M16-01) | in force | `src/engine/dashboard.rs` `describe`, `task_lines`; `src/term.rs` `frame_text`, `screen`; `src/engine_cli.rs` `dashboard` |
| **X36** | One task at a time runs its check gates on a machine (O-23): every task's verify folders (checkout, `TORYO_VERIFY_BUILD`, caches, temp, home) are labelled Low, so the code under test of one task could write another's while both verify. The verify stage takes an exclusive OS file lock, `<data dir>\locks\machine\verify.lock` (a folder no task id or environment lock can name), after its preflights and before the checkout is reset, and holds it over the check gates and the checks of the checkout after them (mutation, left-over files, the hashes of the scripts that ran); it is released before the environment gates, which read a fresh export no Low code can write (X6) and queue on their own lock as before (M11-E3: a long deploy does not hold up another task's build) — a task never holds both locks, so no two tasks wait for each other. When no environment gate follows (none is defined, or a check gate failed), the one check of the checkout is made before the lock is released (M16-R1). The re-check of the checkout after the environment gates runs without it: another task's Low code can only add a `verify_mutated_tree` there, never hide one (the check before the environment gates was made under the lock). Waiting is like an environment lock's: one `lock_waiting` event (`lock: verify`, `holder`: a task in `Verifying` whose owner is alive), `status` shows it, a `toryo stop` ends the wait and the attempt is `interrupted`. (M16-02) | in force | `engine/lock.rs` `VerifyLock`, `verify_lock_path`; `engine/runner.rs` `verify_lock`, `verifying_now` |
| **X37** | Several tasks run as several processes, never as threads of one: `toryo run A B …` starts one `toryo run <id>` child per task (same binary, `--config`, `--machine-config`, drive flags; `--color never` into the pipe), at most `--jobs` (1–8, default min(ids, 4)), queued in the order given. A child is exactly the one-task `run` — its own task lock, recovery, Ctrl+C handling (X29), `run_ended` — so no engine state, interrupt flag or recorder is shared between tasks; what they share on the machine is guarded where it is shared (the store's WAL and busy timeout, environment locks, the verify lock X36). The ids are checked before anything starts. The parent prints the children's lines behind `<id> │`, ends with one block (state, exit code, next action per task) and exits with the highest exit code; on Ctrl+C it starts no queued task and waits for the running ones. One id is the in-process `run` of before. Dependencies between tasks are not scheduled. (M16-02) | in force | `src/run_cli.rs`; `src/main.rs` `Cmd::Run` |
| **X38** | `toryo goal split` proposes, the owner creates. One read-only turn of the planner seat (or `--profile`; R51 evidence as for a task turn) answers `goal-split.schema.json` in a throwaway detached worktree of the base commit under `<data dir>\goals\` — never the owner's checkout, removed on every exit (a Codex seat runs `workspace-write` even when its role only reads); its context is the project's sources with the embedded `goal-splitter.md` role text instead of `planner.md`, and no `.toryo/roles/planner.md` override. The output is files and `GOAL-SPLIT.json` (with the waves); no task is created and no dependency is scheduled — a dependent task is created after its dependency is merged, so its base holds the work. (M16-03) | in force | `src/engine/goal.rs`; `src/goal_cli.rs`; `engine/context.rs` `Request::template` |
