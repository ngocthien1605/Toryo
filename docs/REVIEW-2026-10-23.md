# Toryo — architecture and code review (2026-10-23)

`main` @ `fda36de`, clean working tree (STATUS.md was last updated at `5d0a4e1`, after M16). Baseline measured here: `cargo clippy --locked --all-targets -D warnings` clean with and without `m0-kit`; `cargo test --locked`: 809 passed, 0 failed, 10 ignored. Method: six area reviewers (runner 1–2600, runner 2600–5900, store/lock/recovery/task, config/team/context, agents/process/runner.rs, CLI/views/flight/term) plus the lead re-reading every Medium finding in the code. Known items (STATUS §4 O-nn/N-nn, review 2026-10-01 ids) are cited, not restated.

## Verdict

One High finding, C0: a blanket `toryo resume` can take a stale row as the owner's deploy "yes" and deploy agent-written code without the confirmation the owner configured. It is High because it defeats a safety stop, as the 2026-10-01 review rated fail-open checks; it is not Critical because no agent input triggers it (the owner must run a blanket resume while another process drives the task). Fix it before the first real task with a `confirm:` environment gate. No Critical finding. Everything else is safe to run with. The trust boundary (machine vs repository config, the anchor, the export comparison, M18) held up under adversarial reading. What the review found is a layer below: owner-workflow traps (a task that can be bricked by a config typo, an escalation that loops the owner, a stop that throws away a finished deploy), fail-open reads on the trusted side, and the maintainability debt STATUS already names (O-39, N-10) now with a concrete shape.

## Findings — correctness and edge cases (priority 1)

Severity Medium unless marked (C0 is High). Tag: `read` (from the code, lead-verified) or `reproduced` (a probe was run).

C0. **`toryo resume` without an id can confirm a deploy (X17 bypass).** `engine_cli.rs:1295-1313`: the no-id loop snapshots `list_tasks` once and tests `waits_for_a_deploy_yes` on that stale row, before taking the lock. `resume_one` (`:1115-1130`) re-reads the row but refuses the deploy case only under `--yes`; `resume_before_drive` (`:1213-1230`) then calls `store::confirm_deploys` and the deploy runs. Scenario: a blanket `toryo resume` is driving task A for tens of minutes; meanwhile `toryo resume B` in another window stops B with `environment_gate_confirm` and exits; the loop reaches B, its snapshot says another class, the lock is free, and the plain resume is taken as the owner's yes. The comment at `:1303-1304` says this must never happen. `read`, lead-verified. Fix: pass a `blanket: bool` into `resume_one` and re-test `waits_for_a_deploy_yes` on the fresh row under the lock. This is the most important finding of the review: it is the only one that runs agent-written code in the owner's environment without the confirmation the owner configured.

C1. **A non-finite budget weight bricks a task after `task create`.** `config.rs:952` `canonical_json` uses `serde_json::to_value`, which turns `.inf`/`.nan`/`1e400` in `pipeline.budget_weights` into `null`; `config.rs:933` `from_frozen` refuses `null` for `f64`. `task create` succeeds; every later `run`/`resume`/`status`/`task config --reload` fails "parsing the frozen config.json". Only `task cleanup` works. `reproduced`. Fix: refuse non-finite and ≤0 weights in `problems()`; make `canonical_json` fail on a value JSON cannot carry.

C2. **`approval_mismatch` sends the owner into a loop.** `runner.rs:5757-5765` `withdraw_final` escalates with `store::transition`, so `machine.reason_class` is `None`; `next_action` (`:5829`) falls to the generic branch and offers `approve --gate final --force`; `engine_cli.rs:933-944` gates `--force` on `verify_current` only (still true: the checkpoint did not move, the branch did); `ForceFinal` reopens the gate; the next `approve` hits `approval_mismatch` again. Every lap appends to DECISIONS.md. No text names the exit (reset the branch to the checkpoint). `read`. Fix: `transition_classed(…, Some("approval_mismatch"))`, a `next_action` branch for that class, and `--force` must run the same branch-tip check.

C3. **A 1–3 byte secret destroys the agent stream and the gate text.** `redact.rs:63-97` has no length floor (only empty and newline-only are skipped). A `secret_env` that resolves to `1` redacts every `1` in every JSON line: the Claude/Codex parsers see only `malformed` lines, the turn ends `ProcessCrashed` with no hint, and the fallback chain keys on that class. `reproduced`. Fix: refuse secrets shorter than ~8 bytes at config load (fail at `task create`, not in the turn).

C4. **The context loader treats every read error as "not found" (fail-open).** `context.rs:212-219` `Err(_) => Ok(None)`. A `CLAUDE.md`, `AGENTS.md`, `.toryo/context/*.md`, `CULTURE.md` or `instructions.md` that exists but cannot be read (ACL, sharing violation, a directory of that name) is silently left out of the agent's context, reported as "skipped, not found". `read`. Fix: only `ErrorKind::NotFound` is skipped; anything else is `unreadable` → `context_unreadable` (already machine-caused, X8).

C5. **A stop that lands after a gate finished discards the result; a passed environment gate deploys again.** `runner.rs:2399-2416`: `deployment_end(ok)` is written and the lock dropped, then `if stop.stopped() { return Ok(EnvGates::Stopped) }` before `results.push(entry)` (`:2429`). The attempt is `interrupted`, no `VERIFY_RESULT.json`; the next `resume` re-runs every check gate and deploys the same commit a second time (with `confirm: always` no new question — the row is already confirmed). Check gates have the same shape at `:2237`. Extends N-05. `read`. Fix: once `res` is in hand, record the entry first, then return `Stopped`.

C6. **`task create` rollback removes the row before the worktree.** `task.rs:330-365` `Made::drop`: the DB row goes first; when `worktree remove --force` and `remove_dir_all` both fail (file in use, antivirus), the row is gone, so `task cleanup <id> --force` — the tool for this — says "no task", and re-creating the same `TASK.md` is refused ("worktree already exists"). X28's promise does not hold on this path. `read`. Fix: remove the row last. Related (Low): `task create` installs no Ctrl+C handler (`catch_interrupt` is only in `drive`), so a Ctrl+C during `git worktree add` skips `Made::drop` entirely.

C7. **Hot polls take the SQLite write lock for pure reads.** `lock.rs:119-122` (`stop_requested`), `:149` (`StopWatch`, once per second), `:75` (acquire retry), `:572-601` (`stop`, every 250 ms), `recovery.rs:118`, `runner.rs:2487-2493` (`deployments` lookup) all use `Store::call` (BEGIN IMMEDIATE) for SELECTs. `Store::read` exists and `verifying_now` (`runner.rs:2558`) and `engine_cli.rs:1867` already use it. With `toryo run A B C …` up to 8 processes contend for the write lock every second; the store actor is one thread per process, so the engine's own writes queue behind a poll waiting in the busy handler; the `?` at `lock.rs:122` turns a 15 s BUSY into a failed drive. `read`. Fix: `Store::read` for every read-only job.

C8. **A read-only turn whose process errored escalates without any recorder event.** `runner.rs:2913-2930`: `finish_attempt` + `store::transition(Escalate)` with no `rec.transition_classed`, no `stage_finished`, no `agent_ended`. The task is `Escalated` in SQLite; `events.jsonl`, `watch` and the dashboard show only `run_ended error`. `read`. Fix: route through the one attempt-closer (A1 below).

C9. **`end_with` never persists the escalation class; `finish_classed` does.** `runner.rs:3403-3417` passes `class` to the recorder only while the store gets plain `transition`. Every escalation through `end`/`end_and` (`InvalidOutput`, `policy_violation`, `protected_config_changed`, `implementer failed`, `ReviewBlocked`) has `machine.reason_class == None`; `next_action` falls back to parsing reason text (`:5821-5825`, including `why.contains("PolicyRefusal")`, which matches vendor-written detail). Harmless today only because none of those classes is in `MACHINE_CAUSED`; the first one that is would lose plain `resume`. Low now, latent Medium. `read`.

C10. **`TaskLock::acquire`'s dead-owner retry cannot fire after a clean exit.** `lock.rs:83` retries only when a recorded owner is dead; `Drop` clears the owner columns first and Windows releases the file lock lazily, so `toryo resume T-1` started right after `toryo run T-1` ends sees `WouldBlock`, no owner, `dead = false` → `task_active (owner ?, since ?)`, exit 3. The crash case works, the common case does not. Low-Medium. `read`. Fix: retry also with no recorded owner; `unlock()` explicitly in `Drop` after `clear_owner` (review L9).

C11. **`decide_review` publishes DECISIONS.md follow-ups and `last_reviewed_head` before the decision transition.** `runner.rs:2784-2830`: five transactions and two file writes, then `end_and(decision)`. A crash between leaves an "approved with open issues" record in an append-only file while the task is still `Reviewing` and the resumed reviewer may answer `changes_requested`. Reverse of review M10. `read`. Fix: `set_last_reviewed` inside the closing transaction; append follow-ups after it (as `approve_now` does).

## Findings — architecture (priority 2)

A1. **Seven attempt-closers with three class semantics.** `end`, `end_and`, `end_with`, `finish_and`, `finish_classed`, `escalate_attempt`, plus `escalate`/`apply_with` for the no-attempt case. They differ only in: whether a `StageOutcome` supplies class/detail/session, whether the class reaches the machine (only `finish_classed`/`escalate`), which lines print, and whether `stage_finished` is emitted. Three of them read `self.task()` only for `from`, which `store::transition` already reads and throws away (`store.rs:812`). C8 and C9 are the direct result. Shape: one `Close { status, end, outcome: Option<&StageOutcome>, feedback, event, class: Option<EscalationClass>, in_tx: Option<FnOnce(&Transaction)>, print }` applied by one `close(&self, a: Option<&AttemptRow>, c: Close)` that always calls `transition_classed`, always emits `stage_finished` when there is an attempt, and takes `from` from the transition's return. The six names become one-line constructors. (Mt2 names the duplicates; this is the fix.)

A2. **Escalation classes are strings in seven files (N-10).** The full literal list, collected: `InvalidOutput`, `budget`, `policy_violation`, `protected_config_changed`, `artifact_tampered`, `skill_unavailable`, `context_unreadable`, `context_over_budget`, `{role}_quota`, `implementer_quota`, `quota exhausted`, `implementer failed:`, five `HeadGuard` kinds, `environment_gate_timeout`, `environment_gate_unavailable`, `environment_gate_confirm`, `same_vendor_review`, `approval_mismatch`, `subject_changed`, `recovery_policy_violation`, `PolicyRefusal` (substring match), `format!("{class:?}")` of `ErrorClass` (CamelCase, snake_cased later), the sentinel `UNDO_PENDING` matched with `contains`. Shape: `enum EscalationClass` in `state.rs` with `as_str`/`FromStr`, `is_machine_caused()` as a method (keeping the `MACHINE_CAUSED` unit test), `Ev::Escalate { class, reason }`; `next_action` branches on the enum; `pending_undo` becomes a typed flag on `AttemptEnd`, not a substring in `error_detail`.

A3. **`runner.rs` (7,250 lines) split.** The natural cuts, in dependency order: `engine/core.rs` (Engine, `run`, `apply`, the one closer), `engine/budget.rs` (`admitted`, `weights`, `billing`, `usage`, the on_usage hook — the R41 arithmetic in one place), `engine/anchor.rs` (`start_at_anchor`, `anchor_of`, `HeadGuard`, `finish_pending_undo` — shared with `recovery.rs`, which today imports them from `runner`), `engine/stage_plan.rs`, `engine/stage_implement.rs`, `engine/stage_checkpoint.rs`, `engine/stage_verify.rs` (preflights, `VerifyAt`, gate running) and `engine/envgates.rs`, `engine/stage_review.rs` + `engine/read_only.rs` (`read_only_turn`, `undo_read_only_write`, `TreeState`), `engine/machine_locks.rs` (`env_lock` and `verify_lock` are ~90 % one loop: try-acquire, wait bookkeeping, holder lookup, 100 ms stop polling — one `wait_for_lock(try, name, holder_of, stop)`), `engine/gate_decisions.rs` (`approve_now`, `reject_now`, `withdraw_final`, `next_action`, `write_summary`). `Result<Result<StageOutcome, Flow>>` and `ReviewTurns::Ended(Flow)` are the same idea one level apart: `enum Turn { Done(StageOutcome), Ended(Flow) }`. `gate_name` exists three times (runner, store, flight): `GateKind::name()`.

A4. **`store.rs` (2,158 lines) and `lock.rs`.** `store/` → `mod.rs` (actor, open, migration), `schema.rs`, `tasks.rs`, `attempts.rs`, `usage.rs`, `control.rs` (locks + stops), `artifacts.rs`, `deploy.rs`; pull the raw SQL at `runner.rs:3257` into it; a `&ReadTx` newtype for read-only helpers would make C7 a compile error. `lock/` → `task.rs` (TaskLock, StopWatch, `stop`), `interrupt.rs` (Ctrl+C), `machine.rs` (EnvLock, VerifyLock, name rules). `transition_classed` reads the task row three times (`store.rs:801-805`).

A5. **`config.rs` (2,745 lines, 1,250 of tests) and `team.rs` (2,843).** `config/types.rs`, `config/effective.rs` (load/freeze/validate), `config/guard.rs` (`machine_only_part`, `refuse_tags`, `untagged`), `config/env.rs` (`expand_vars`, `residual_var`, `data_dir`), `config/secrets.rs`; `denied_override`/`resets_provider` encode Codex `-c` policy and belong beside the Codex adapter; `not_a_repo_path` is shared with `team.rs` and `checks::fence_pattern` (one `paths` module). Validation is spread over load, `doctor`, `task create` and `task config --reload` with different subsets; `instructions` and `culture` path validity are checked twice (two problem lines for one key); seat→profile existence has two UX (`bail!` at the first vs all at once). One `admit(cfg, repo, base)` used by create/reload/doctor.

A5b. **`engine_cli.rs` (2,071 lines, bin crate, O-39/Mt3).** `resume_before_drive`, `machine_caused_stop`, `waits_for_a_deploy_yes`, `environments`, `driven_owner`, `cleanup_would_lose`, `recovered_events`, `run_ended`/`end_outcome` and `facts_with` touch only `Store`/`TaskRow` and belong in the library (`engine/commands.rs`), where C0 would be unit-testable. The preamble `store()?; TaskLock::acquire; get` repeats seven times: a `with_locked(id, |st, lock, t| …)` helper. The dashboard frame assembly belongs in `engine/dashboard.rs`.

A6. **Sound, verified, no change needed:** the pure state machine (every state mapped in `next_action`; `Reverify`/`ForceFinal` guards hold); the store actor (no nested `call` in 160 sites — a thread-local "inside the actor" assert would keep it so; `catch_unwind`+ROLLBACK unreachable but harmless; no pending write at exit); `approve_now`/`reject_now` under the task lock; the Held/VerifyLock drop order (X36/X39); the turn loop (`Ok(None)`, `cancel: None`, `stall > max`); pipe draining (own reader thread per stream); `BoundedOutput` memory (64 KiB chunks); `bounded_text` char-boundary loops; Job Object flags; `git.rs` argument handling; serde_yaml billion-laughs/nesting/merge-key/duplicate-key behaviour on repository files (`reproduced`); the frozen-config JSON round-trip (every `skip_serializing_if` has a `default` partner, keys sorted); `run_cli` child argv and the exit-code fold; the `goal split` Markdown escaping and its re-parse before writing; the throwaway worktree removal on every exit path; `notify.rs` (no interpolation: the text travels in environment variables and becomes XML text nodes); the flight recorder's torn-line handling and per-process `ts` monotonicity.

## Findings — performance (priority 4, low)

- Per `Checkpointing` pass the protected scan walks the whole tree three times (`run()` top, `protect::check`, `take_baseline`) plus once in `interpret_implement` — N-06/O-18 territory; `take_baseline` could accept the `Scan` that `check` just made.

- `expand_vars`/`residual_var` compile their regex per call; `Effective::load` parses `toryo.yaml` three times.
- Each agent stdout line is JSON-parsed up to three times (`exec.rs:399`, `events.rs:82`, the parser); `resume_main_thread` takes a system-wide thread snapshot per spawn; `BoundedOutput::push` extends the `VecDeque` byte by byte.
- `decide_review` makes ≥5 transactions + 2 artifact publishes per review (C11 fixes this too).
